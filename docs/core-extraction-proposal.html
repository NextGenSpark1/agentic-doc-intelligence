NextGen Document Intelligence Suite · Architecture Proposal

Shared Core Extraction

How we make the Investigation Intelligence backend reusable for Tendering Intelligence (and future products).

01

The core idea

We don't copy the repo into a new folder for tenders (a "fork"). A fork means two copies of the same document pipeline that slowly drift apart — every bug fix has to be done twice.

Instead, reorganise the one existing backend into two parts — a shared engine, and the product-specific logic built on top of it.

CORE — shared engine INVESTIGATION — today's product SPLIT — has both, must be divided

"Drops in" simply means reuse almost unchanged — like a LEGO piece that already fits. Most of the backend drops into core/ as-is. A new product mainly adds its own schemas, prompts, and a few new stages, and borrows everything else.

04

How the 3 split files divide

The golden rule: the engine (the HOW) goes to core/; the content (the WHAT — labels, rules, schemas) stays in the app and is passed in as an argument.

classify.py — pass the type list in

The classify logic (ask the LLM, fall back to keywords) is generic. Only the list of document types is domain-specific.

→ coreclassify(md, known_types, heuristics) — the engine
→
→ each apppasses its own list: Investigation → invoice, bank_statement…; Tendering → tender_notice, BOQ…

db.py — split by table

→ core/db_core.pyget_client, _content_hash, and all cases / documents / chunks / match_chunks queries
→
→ app/db.pyfindings / relationships / entities queries — imports get_client from core

main.py — split by route (FastAPI routers)

We already do this once — orgs.py uses app.include_router(). Apply it more widely.

→ core/main.pythe app + shared routes: health, auth, /cases, /documents, /chat
→
→ app routers/findings, /entities, /timeline — wired in via include_router()
No behaviour change

Investigation runs exactly the same afterwards. Code is moved, and content is passed as arguments instead of hardcoded.
