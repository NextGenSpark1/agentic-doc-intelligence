Extending the Core for Tendering Intelligence

How the Tendering Intelligence product is built as a configuration-and-schema extension of the existing Investigation Intelligence pipeline — one document-processing core, two domain apps. No second OCR, embedding, vector-search, or citation pipeline.

01

The extension mechanism

The codebase already has the seam we need. Three of the four extension points exist today; one has to be built. That gap is the actual engineering in this plan.

Investigation Intelligence already routes behaviour by case_type. A tender workspace is simply a new domain that registers against the same seams:

 NEW seam The one real gap. The orchestrator hard-codes its five stages. It must become a registry keyed by domain so a workspace runs its own stage list.
The decision this plan turns on

run_case_analysis today is a fixed sequence: resolve_entities → build_relationships → reconstruct_timeline → detect_anomalies → summarise. Tendering needs a different sequence. The fix is not an if domain == "tender" branch — it is a stage registry: each domain declares an ordered list of stage callables, and the orchestrator just runs whichever list the workspace's domain points to. Investigation keeps its five; Tendering declares its own. This one refactor is what makes everything below "config, not fork."

Proposed package shape

Rename the shared modules into a core/ boundary and let each product be a thin domain package. Nothing moves that isn't already shared; the split just makes the boundary explicit and stops drift.

Sequencing risk — raise with the team

The core/ extraction must land before tender stages are written. If Tendering is built as a sibling of Investigation with "extract the core later," later never comes and you maintain two forks by Q4. Do the boundary first, on the current green codebase.

Conflicts & duplication to resolve

1. Tender vs. cases (collision). The roadmap models Tender as a top-level entity; the core already has cases doing exactly that job (org scope, documents, findings, chat, access control via _load_case_or_403). Do not build a parallel workspace table with its own access logic — that duplicates the tenant-isolation surface. Recommendation: add a domain column to cases and reuse every access/audit path already hardened for it.

2. Requirement vs. findings (near-duplicate — deliberate). A Requirement and a finding share a shape: AI-extracted, source-linked (doc/page/clause), confidence, human validation state. Don't fork the review logic twice. Generalise the "AI-extracted record pending human review" pattern (status, reviewed_by, source refs, content-hash dedup) into a base both specialise. This is the single most valuable abstraction in the whole extension.

04

Enforcing the hard rules in the design

The three non-negotiable rules are not new work — the core already enforces the shape of all three. Tendering inherits the enforcement; here is exactly where it lives.

RULE 2Every AI finding needs source + confidence
  • The llm_reasoning.ask() guardrail already drops any output citing a document/entity/event not sent to the model — ungrounded findings never persist. Requirements inherit this unchanged.
  • Chunks carry page + bbox from ADE visual grounding; the Requirement schema makes source_document, page, clause, confidence required, not optional — an extraction missing them is rejected at validation, not rendered.
  • Enforced at the schema layer (Pydantic) so the rule can't be bypassed by a prompt change.
RULE 3AI extracts / suggests / flags — never auto-decides
  • Reuses the existing human-review state machine: every AI record lands pending. A person moves it to validated/rejected — the API has no path that auto-confirms.
  • Evidence links carry an ai_relevance_score but require user_approval_status before they count toward a submission — the AI suggests, the bid team approves.
  • Bid/no-bid and readiness are recommendations with a score; no endpoint marks a tender "compliant" or "submitted" from an AI call. The decision write is always user-initiated and audit-logged.
RULE 4Strict tenant isolation across every surface
  • DB & API: reuse _load_case_or_403 + org/role scoping already hardened this session — every tender route goes through it, including the new requirement/vault/evidence endpoints.
  • Vector search & AI retrieval: match_chunks is case_id-scoped today; the new evidence-match retrieval must be org_id-scoped so one supplier's vault is never searched for another. This is the one isolation surface to design in from line one, not retrofit.
  • Storage: continue the {case_id}/{doc_id}/ path convention with signed URLs behind the access check; vault files scoped under {org_id}/.
  • Logs, caches, background jobs: audit rows already carry org_id; background analysis is invoked only through access-checked endpoints, so a queued job inherits the caller's scope.
