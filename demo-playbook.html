03

What makes it defensible

The five things a generic "AI + PDFs" demo can't say.

Visual grounding trust

Every extracted value and every chat citation carries the source page and bounding box. Click it, see it highlighted on the original document. For legal and forensic work, "show me where" is non-negotiable — most tools can't.

AI-first, rules as a safety net reliability

LLM cross-document reasoning is the primary engine. When the model is unavailable, deterministic, unit-tested rules (duplicate invoices, shared bank accounts, split payments, budget-ceiling proximity) take over. The system degrades gracefully instead of going dark.

Anti-hallucination guardrails integrity

Any AI output that cites a document, entity, or fact we didn't actually send is dropped before it's ever stored. The model can connect the evidence we have — it cannot invent evidence we don't.

Human-in-the-loop + audit governance

Findings stay "pending" until an investigator confirms or dismisses them with a reason. Reports use confirmed findings only. Every step — extraction, analysis, review — is written to an audit log.

Domain-configurable extraction reach

What the system pulls from each document is defined by a schema you edit in the UI — a field name plus a plain-English description. Add "beneficiary_iban" or "policy_number" and the engine extracts it. No redeploy.

Provider-swappable AI core flexibility

All model access runs through one router. Reasoning, classification, and embeddings each point at a configurable model string — swap Groq for an on-prem or client-hosted model without touching the pipeline. Matters for regulated buyers.

05

Customizing for other use cases

The horizontal play — the same engine, new verticals.

The instinct in the room will be "this is a fraud tool." It isn't — it's a cross-document reasoning engine that currently ships a fraud-investigation configuration. Everything except the extraction schema and a handful of domain rules is generic. Here's how much effort each level of customization actually takes.

Level 1 · no code

Reconfigure the schema

Effort: minutes, in the UI

Define a new case type and its extraction fields — each a name plus a plain-English description of what to pull. The entire pipeline (extract → entities → relationships → timeline → findings → chat → report) works unchanged. This is the lever to demo live.

Level 2 · prompt tuning

Retarget the reasoning

Effort: hours

Adjust the analysis prompts so the AI hunts for a domain's specific red flags — inflated claims, coverage gaps, coding mismatches — and add document classes. No architectural change; it's editing the questions the engine asks.

Level 3 · engineering

Add rules & integrations

Effort: days+

Codify domain-specific deterministic checks that must survive audit, wire in external data (sanctions lists, registries, claims systems), and add bespoke report/export templates for the client's process.

Tech

"How do you stop it from hallucinating findings? That's a lawsuit in this domain."

Two layers. Grounding: any AI output citing a document, entity, or fact we didn't send is discarded before storage — the model can only connect evidence we actually have. Human gate: findings are proposals, not conclusions; nothing reaches a report until an investigator confirms it, with every extraction traceable to a highlighted spot in the source. We treat the AI as a very fast junior analyst whose work is always checked.

Tech

"Why not just give an investigator ChatGPT and a folder of PDFs?"

A chat model reasons over what you paste into one window — it has no concept of the case. It can't resolve that "A. Zulkifli" in one file and "Ahmad Zulkifli bin Hassan" in another are one person, can't build a graph or timeline across a hundred documents, can't show you the pixel a claim came from, and keeps no audit trail. Our value is precisely the case-wide layer on top of extraction — plus the governance a regulated buyer requires.

Tech

"What's real today versus staged for this demo?"

Real and working: auth, upload, extraction, the full 7-stage pipeline, visual grounding, RAG chat, findings review, entity graph, timeline, and report generation — end to end. Honest caveats: it runs on developer infrastructure and free-tier AI quotas, so it's a working system, not yet hardened for paying customers. Solutions

"How fast can we stand this up for a specific client's use case?"

A new document type with its own extraction fields is a same-day, no-code change in the UI — the whole pipeline just works against it. Retargeting the AI's red-flag reasoning is hours of prompt work. Only truly bespoke deterministic rules, external-system integrations, or client-specific report formats are a multi-day engineering effort. So a credible pilot in a new vertical is weeks, not a rebuild.

Solutions

"Data security — clients will have highly sensitive documents. Where does it go?"

Evidence sits in the client's storage; access is authenticated. The AI layer is provider-swappable through a single router — for a sensitive client we can point reasoning and embeddings at an on-prem or client-hosted model with no pipeline change. Being straight: today's config uses external AI providers and permissive dev settings, so tenant isolation and a security review are prerequisites before onboarding a real client (section 7). The architecture supports the lockdown; we haven't thrown the switch yet.

Delivery

"What does it cost to run per case, and does it scale?"

Cost is dominated by document extraction and AI calls, both roughly linear in pages and documents — predictable and per-case attributable. It runs comfortably on free/low tiers today; production means paid extraction and AI quotas, sized per client. Scaling is straightforward: the pipeline already runs as async background work and the services are containerized, so we scale horizontally rather than re-architect.

Delivery

Three, all tracked in section 7: (1) per-tenant access control before external users; (2) moving off free-tier extraction/AI quotas onto sized paid plans; (3) extraction accuracy validation on each client's real document set. 07

Honest status & what's left

Say this before they find it. Candor buys credibility.
  • Per-tenant access control
    Blocker for external users
    Login is enforced, but every authenticated user currently sees every case. Row-level isolation per user/team is required before any real client touches it. Straightforward to add on Supabase — just not done yet.
  • Free-tier AI & extraction quotas
    Blocker for scale
    Runs on free/low tiers of the document-extraction and language-model providers, which rate-limit and can stall large cases. Production needs sized paid plans — a budgeting decision, not an engineering one.
  • Rule findings suppressed when AI answers
    Design tension
    Current wiring is AI-first: the provable rule-based checks (duplicate invoice, shared bank account) only run when the AI returns nothing. We likely want both to run and merge so the deterministic, audit-safe findings always appear. Known; fixable.
  • Extraction accuracy varies by document
    Needs validation
    Accuracy depends on document quality (scans, unusual layouts). Each new client needs a validation pass on their real documents before we quote accuracy. Visual grounding makes errors easy to spot and correct — but a human still verifies.
  • Permissive dev configuration
    Housekeeping
    Cross-origin access is wide open and secrets live in local config — fine for a demo, tightened before deployment. Standard pre-production checklist.
08

Demo-day checklist

Run this an hour before. Don't wing the live parts.

Pre-flight

  • Seed a compelling case in advance — 4–6 varied documents that actually trigger cross-document findings (shared account, duplicate invoice, a suspicious timeline). A boring case is a boring demo.
  • Pre-run the extraction and analysis so findings, graph, and timeline are already populated — then re-run one piece live for effect.
  • Verify AI keys and quotas are live today. Confirm at least one full analysis pass completes without hitting a rate limit.
  • Rehearse the field-click-to-PDF-highlight (step 4) until it's smooth. It's the money shot.
  • Have the report pre-generated in a second tab as a fallback in case live generation is slow.

Live-demo discipline

  • Lead with grounding, close with the report. Wow early, ROI last.
  • Narrate the "why," not the UI. They don't care about buttons; they care what each moment proves.
  • Volunteer the limitations from section 7 before they probe — it makes every claim more believable.
  • Keep the corpus small on screen. Enough to be impressive, few enough to stay legible.
  • Park deep-tech tangents. "Great question — let me show one more thing, then go deep." Protect the arc.

If something breaks live

Don't debug in front of the room. Switch to the pre-run case and pre-generated report, say "let me show you the completed version," and keep the narrative moving. The story survives a failed API call; a five-minute silence in front of the co-founder does not.
